    Recipes¶

    Introduction¶

    A recipe is a ready Bhaskera configuration for one model, using the fastest strategy measured on PARAM Rudra.

    Model QLoRA + DDP LoRA + DDP Pipeline HSDP FSDP2
    Qwen/Qwen3-14B qwen3-14b-qlora qwen3-14b-ddp qwen3-14b-pipeline qwen3-14b-hsdp qwen3-14b-fsdp
    Qwen/Qwen3-30B-A3B-Instruct-2507 (MoE) qwen3-30b-a3b-qlora qwen3-30b-a3b-ddp qwen3-30b-a3b-pipeline qwen3-30b-a3b-hsdp qwen3-30b-a3b-fsdp
    meta-llama/Llama-3.3-70B-Instruct llama-3.3-70b-qlora — llama-3.3-70b-pipeline llama-3.3-70b-hsdp llama-3.3-70b-fsdp
    mistralai/Mistral-Large-Instruct-2411 mistral-large-123b-qlora — mistral-large-123b-pipeline mistral-large-123b-hsdp mistral-large-123b-fsdp
    Qwen/Qwen3-235B-A22B-Instruct-2507 (MoE) — — qwen3-235b-a22b-pipeline qwen3-235b-a22b-hsdp qwen3-235b-a22b-fsdp

    Each file is recipes/<name>.yaml, shown in full under Full Recipes. The fastest one for each model is in Benchmarks; in short, QLoRA + DDP for the dense 14 B to 123 B models and Pipeline for the MoE models. Node counts: any for DDP, QLoRA and FSDP2. Pipeline needs 2 GPUs per node to add up to a whole number of stages (4 stages: a multiple of 2 nodes, 8 stages: a multiple of 4, 16 stages: a multiple of 8). HSDP needs a whole number of shard groups (a group of 4 GPUs: a multiple of 2 nodes, a group of 16: a multiple of 8).

    How the recipes relate to the benchmark

    The speed and memory in each header are the measured benchmark numbers for that model and method. The recipes were written to the same settings (LoRA rank 16, sequence length 4096, the shard group sizes above) and every one loads cleanly in Bhaskera's configuration check, but a recipe is a starting point: run DRY_RUN=1 ./submit.sh recipes/<name>.yaml <nodes> 1 first, which checks the model, data, GPU memory estimate and node count without submitting.

    A pipeline recipe splits the model into stages on different GPUs, so the number of GPUs (2 per node) must be a multiple of the number of stages. submit.sh checks this before it submits.

    Full Recipes¶

    Every recipe in full, for reference. Open one, copy it to recipes/<name>.yaml in your run folder (they are already there when you copy the kit), replace <project>/<username> and the two tokenised data paths, and run it. The comment lines at the top give the measured speed.

    Reading a recipe

    • model: the model folder, precision, attention and kernel choices, and quantization: qlora for 4-bit.
    • data: the tokenised caches (tokenized_path, val_tokenized_path), seq_len and runtime_packing.
    • lora: the adapter (r, alpha, which modules). moe: router settings for mixture-of-experts models.
    • training: batch size, learning rate, max_steps, and distributed.strategy (ddp, fsdp or pipeline, with hsdp_shard_size for HSDP and stages / microbatches for pipeline).
    • checkpoint, logging, monitoring: where checkpoints go and how often, the MLflow run name, and the metrics recorded.

    Full Fine-tuning (Training Every Weight)¶

    Every recipe above trains a LoRA add-on: the model stays as it is and a small adapter is trained, which is what makes 14 B to 235 B models practical. To train every weight instead, set LoRA off and use a method that spreads the model over the GPUs:

    lora:
  enabled: false
training:
  lr: 1.0e-5                      # much lower than the 1e-4 of LoRA
  distributed:
    strategy: fsdp                # fsdp (FSDP2), or ddp for a model that fits on one GPU; hsdp also works
checkpoint:
  enabled: true                   # the result lives in the checkpoints, so keep this on
logging:
  mlflow_log_adapter: false       # there is no adapter to keep

    Choosing Nodes and Hours¶

    Checkpoints. A checkpoint holds the trained LoRA weights and the optimizer state. With QLoRA + DDP, DDP and FSDP recipes it is written when the run ends, either at max_steps or at the end of an epoch (checkpoint.save_interval counts epochs). With Pipeline recipes it is written every save_interval steps (500 in the recipes). Resubmitting a job with the same checkpoint.save_dir continues from the latest checkpoint, and the learning-rate schedule continues with it.

    So a QLoRA, DDP or FSDP run that is longer than the partition's time limit has to be split by hand: set max_steps so that each job ends before the limit, and resubmit with a larger max_steps to continue.
